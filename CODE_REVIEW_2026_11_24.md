## Findings summary

**80 unique findings** (85 raw, 5 duplicate reports merged into their root-cause findings): **0 critical, 11 high, 54 medium, 15 low.**

Every high finding was independently spot-checked against the source by the orchestrating reviewer before inclusion. Likely false positives were discarded silently per the review rules; notable adjudications are listed at the end.

**Main themes:**
1. **Cancellation & lifecycle gaps in the chat pipeline** — Stop/delete/conversation-switch during generation can finalize the wrong message, truncate a new response, or crash on an invalidated SwiftData model.
2. **Crash-on-input defects** — `parseThink` tag-order trap, unvalidated audio-tap format with no macOS mic-permission path, `selectedModel!` in the floating panel, corrupted-vector decode traps, failed `sqlite3_open` left armed to segfault.
3. **Knowledge (RAG) integrity** — watcher prune can delete live index rows (residual edge of the deliberate K-D5 fix), off-thread `NSMetadataQuery` access, non-transactional ingest, claim leases never renewed, chunk-cap violations, and a deflate-bomb OOM on untrusted DOCX files.
4. **Privacy** — speech recognition is not forced on-device (`requiresOnDeviceRecognition` never set), so mic audio goes to Apple servers by default despite the local-only design.
5. **Entitlement/sync wiring** — mid-session Plus purchase never re-resolves the Knowledge root (iCloud inert until relaunch); Free-tier document gate counts indexed docs (always 0 on iOS) so the paywall never triggers there.
6. **Destructive error swallowing** — settings "Cancel" persists edits, delete-all silently wipes models too, export/import report success on failure, share-extension import failures complete as success.

## High severity (11)


### `Molten/Knowledge/Process/Extractors.swift:250-267` — security

inflateRawDeflate has no decompressed-size bound: it starts at input.count*4 and multiplies capacity by 4 for up to 10 iterations (up to ~4^10 x input, i.e. ~1,000,000x) whenever compression_decode_buffer fills the buffer. DOCX files are untrusted user input (Files app, share extension). A crafted .docx whose word/document.xml is a deflate bomb (deflate reaches ~1000:1; e.g. 10 MB compressed -> multi-GB expanded) makes the loop allocate Data(count: 16GB+) -> malloc failure/jetsam kills the app while indexing. Even a legitimately huge document.xml forces hundreds-of-MB zero-filled allocations per retry. Fix: cap total decompressed bytes (and derive the expected size from the ZIP central directory) instead of unbounded x4 growth.

### `Molten/Knowledge/Process/KnowledgeBackgroundTask.swift:25-34` — bug

The expiration handler completes the BG task but never cancels the processing Task (which is unstructured and not stored anywhere), and KnowledgeIndexer.scan/process, Chunker, and EmbeddingService contain no Task.checkCancellation at all (verified by reading them). Two concrete failures: (1) when the system expires the task during a long index, expirationHandler calls setTaskCompleted(success:false) but the for-loop keeps indexing afterwards and eventually calls setTaskCompleted(success:true) a second time on the already-completed/expired task - completing a BGTask twice is a programmer error per the BGTaskScheduler contract (exception/crash risk), and side effects continue after the system reclaimed the task; (2) even if the Task were cancelled, nothing observes cancellation, so expensive OCR/embedding work continues regardless. Store the Task, cancel it in expirationHandler, and check cancellation in the scan loop.

### `Molten/Knowledge/Watch/Watchers.swift:129-144` — bug

NSMetadataQuery is accessed off its run-loop thread. IndexWatcher.start() is called from KnowledgeSync.start(), which is @MainActor (line 174-183), so query.start() attaches the query to the main run loop and notifications arrive on main. But queryUpdated() (line 129-131) spawns an unstructured `Task { await ingestNewOutputs() }` from a nonisolated @objc method; ingestNewOutputs is nonisolated async and therefore runs on the cooperative thread pool, where it calls query.disableUpdates(), reads query.resultCount / query.result(at:), and calls query.enableUpdates() (lines 137-141) while the query can concurrently mutate its internal results on the main run loop. NSMetadataQuery is not thread-safe and is bound to the thread/run loop that started it; disableUpdates/enableUpdates themselves mutate query state. This is a data race on every iCloud sync update for Plus users (possible crash inside Foundation, torn/inconsistent result enumeration, or lost update batching). The result snapshot should be taken on the query's thread (e.g., in the notification handler or via a MainActor hop) before doing background ingest work.

### `Molten/Knowledge/Watch/Watchers.swift:233-247` — bug

Deletion pruning in refreshMapping() removes index rows belonging to LIVE documents. `removeDocument(base:name:)` (KnowledgeStore.swift:237-246) selects documents by base+name only, but `documents` is keyed by hash and the name column holds whichever name was ingested last. Concrete scenario: base 'Work' contains /Work/notes.txt (hash X) and /Work/sub/notes.txt (hash Y) — or two copies of identical content (same hash) at different paths. User deletes one file. The scan phase skips the survivor because its mapping mtime is unchanged (line 211). The prune phase then finds the deleted path gone, removes its mapping entry, and calls removeDocument(base: 'Work', name: 'notes.txt') unconditionally (line 242), which deletes the documents/chunks/vectors rows of BOTH hashes — including the live file. The subsequent stillReferenced hash gate (lines 243-246) cannot undo this because the base+name delete already removed everything. No repair path re-ingests the survivor: refreshMapping skips it (mtime unchanged), IndexWatcher only fires on Index-file metadata changes (deleting a source document touches no .mkt/.mkv), and on iOS there is no launch scan. The live document silently disappears from search and document counts until the file itself is modified (macOS may recover at next launch via KnowledgeIndexer.scan). The same over-broad delete also fires transiently after Free->Plus migration, where stale local-path mapping entries are pruned with base+name values identical to the freshly re-ingested iCloud rows (repair then depends on IndexWatcher ingest winning the race against the prune).

### `Molten/Conversations/AutoTitler.swift:30-53` — bug

titleIfNeeded reads and mutates a SwiftData model owned by SwiftDataService's ModelContext from the AutoTitler actor, outside that context's isolation: line 30 faults conversation.messages (a relationship registered in the data actor's context) and line 51 writes conversation.name. The caller fires this concurrently with persistence of the same objects: ConversationStore.handleComplete (ConversationStore.swift:540-557) launches Task { updateMessage(lastMessage) } on the data actor AND Task { AutoTitler.shared.titleIfNeeded(...) } at the same time, so the AutoTitler executor can fault/read through the ModelContext while the data actor is saving into it — ModelContext is not thread-safe (concurrent use is a Core Data concurrency violation, risking crashes/corruption). ### `Molten/Conversations/ConversationSearch.swift:101-118` — performance

rebuild(conversations:) runs the entire backfill inside one lock with no surrounding SQL transaction: each per-message INSERT (line 108) autocommits as its own transaction with a journal fsync. ### `Molten/Extensions/SplashSyntaxHighlighter+Extension.swift:72-78` — performance

Unbounded synchronous syntax highlighting on the main thread with quadratic Text concatenation. Verified against the vendored dependency: MarkdownUI's CodeBlockView evaluates codeSyntaxHighlighter.highlightCode(content, language:) inside its body-derived label (build/SourcePackages/checkouts/swift-markdown-ui/Sources/MarkdownUI/Views/Blocks/CodeBlockView.swift:26), so highlightCode (lines 20-26) runs synchronously on the main thread on every Markdown render. ### `Molten/Knowledge/Embed/EmbeddingService.swift:50-55` — bug

countTokens falls back to TokenEstimator.estimate (text.count/4) until the model is downloaded, and Chunker uses it to size chunks (target 350 / cap 480 'tokens'). For CJK text e5 emits roughly one token per character, so a '480-token' chunk built pre-download is ~1900 real tokens; even English chunks near the cap can exceed 512 real tokens. embed() then silently truncates to profile.maxTokens (512) via tokens.prefix, and because .mkt outputs are write-once (G4, CoordinatedIO.writeOnce) and never regenerated after the model arrives, those oversized chunks are permanently under-embedded - the tail of every such chunk is invisible to semantic search while remaining keyword-searchable, with no warning. This is a concrete bug inside the documented estimate fallback: either re-chunk documents whose .mkt was produced with the estimator once the real tokenizer is available, or size pre-download chunks conservatively for the worst-case tokens-per-character.

### `Molten/Knowledge/Embed/EmbeddingService.swift:66-96` — performance

embed(texts:prefix:) embeds a document's entire chunk list in one batch: KnowledgeIndexer.process calls embed(passages: document.chunks.map(\.text)) with no sub-batching, and the closure builds a [N, maxLength] token tensor and runs the full 12-layer BERT forward on it before pooled.eval(). Activation memory scales linearly with chunk count (hidden states alone are N*512*384*4 bytes ~ 0.8 MB/chunk; FFN intermediates are 4x that), so a large PDF (e.g. 800-1000 chunks ~ a 1000-page book) peaks at multiple GB and risks jetsam/OOM on iOS and memory pressure on macOS. Additionally, EmbedderModelContainer.perform is a serial access container, so while a whole-document embed runs, Retriever's query embedding for an in-flight chat message queues behind it - grounding (and the user's send) stalls for the duration. Batch passages into fixed-size sub-batches (e.g. 16-32) inside the perform closure.

### `Molten/Knowledge/Embed/HFSnapshotDownloader.swift:61-73` — bug

After a failed hash verification the corrupt file is left at `target`, and the retry path downloads to a temp file then calls FileManager.moveItem(at: tmp, to: target) without removing the existing destination. moveItem throws NSFileWriteFileExistsError when the destination exists, so once any LFS file (e.g. model.safetensors) fails verification once - corrupted/partial download, captive-portal HTML served with 200, proxy tampering - every subsequent ensureModel attempt throws at the move step before it can ever replace the bad file. The embedding model can never become ready again (semantic search permanently stuck in keyword-only) until the user manually deletes Application Support/Molten/Models. Delete/replace the existing target before moving (or write atomically to the target path).

### `Molten/Knowledge/Embed/HFSnapshotDownloader.swift:124-129` — bug

Non-LFS files get no integrity validation at all: FileEntry.sha256 is lfs?.oid, so config.json / tokenizer.json / tokenizer_config.json have nil sha256 and verify() returns true unconditionally (the 'size-only trust' comment is not implemented - entry.size is never compared either), and the download's HTTP response is discarded (`let (tmp, _) = try await URLSession.shared.download`). A captive portal or HF error page returned with status 200 for tokenizer.json is moved into place and accepted; on the next attempt the `fileExists && verify` branch treats it as 'cached and verified - never re-download', so the poisoned file is permanent and model loading fails forever with no recovery path. Check the HTTP status of the download response and validate non-LFS files (at minimum against entry.size, ideally the Hub's non-LFS sha256).

### `Molten/Knowledge/Process/Chunker.swift:77-84` — bug

The documented hard cap (480 tokens incl. prefix, K-P9) is violated on ordinary input. (1) trailingSegments inserts the first reversed segment even when it alone exceeds the 50-token budget (`if tokens + t > budget && !result.isEmpty`), so a 470-token block becomes the entire 'overlap'. (2) In chunk(), a block of up to maxTokens (480) that is not itself oversized is appended to a non-empty current (the overlap) after the target-overflow flush without re-checking maxTokens. Trace: blocks A=470, B=100, C=100 tokens -> chunk0=A(470); flush carries overlap=[A] (budget ignored); current=[A]+B -> chunk1=570 tokens; with a following 480-token block chunks reach ~950 tokens. EmbeddingService.embed silently truncates every sequence to 512 tokens, so the tail of these chunks is never embedded (semantic search misses that content) and the oversized overlap duplicates large text across chunks. Enforce the overlap budget (split or drop oversized trailing segments) and re-check the cap after appending to overlap.

### `Molten/Knowledge/Process/Chunker.swift:172-183` — bug

splitByWords has no fallback for a single 'word' that exceeds maxTokens: when one unbroken token run (a long URL, base64 blob, minified code line, or any whitespace-free string > ~480 e5 tokens) is enumerated as one word, the candidate exceeds the cap but `end > start` is false on the first iteration, so no split happens; the whole run is then emitted as one piece still over the cap. This breaks the chunker's hard-cap contract for reachable document content, and EmbeddingService.embed truncates it to 512 tokens, silently dropping the remainder from the semantic index. Add a character/UTF-16-range fallback split when a single word exceeds the cap.

### `Molten/Knowledge/Process/ClaimStore.swift:98-110` — bug

release(hash:stage:failed:) deletes the claim file unconditionally, without verifying the stored claim still belongs to this device. Scenario: device A claims .extract, then stalls past the 10-minute lease (large scanned PDF; note leases are never renewed in production - see KnowledgeIndexer finding); device B legitimately takes over the expired claim via tryClaim and starts processing; A then finishes or fails and calls release, deleting B's live claim. A third device (or A's next scan) can now claim the same stage while B is still working, defeating the mutual-exclusion protocol; if A failed, release(failed:) also accrues A's attempts and can write a shared .failed marker that blocks automatic retries on every device for work B may complete successfully. release should read the claim and only remove it when claim.deviceID == self.deviceID (same ownership check renew already does).

SwiftUI matches/writes Picker selection only when the tag type equals the selection type; String tags never equal an AppColorScheme selection, so no row ever shows as selected and tapping Light/Dark/System never updates the binding. Concrete failure: user opens Settings > App > Appearance, taps 'Dark' -> colorScheme stays unchanged, appearance does not change, and the picker shows no current selection. The neighboring Default Model and Voice pickers correctly use matching String/String types; only this one mismatches. Fix is .tag(scheme). Evidence: SettingsView.swift:192-195; AppColorScheme.swift:11-16.

### `Molten/UI/macOS/CompletionsEditor/CompletionsEditorView.swift:128-134` — bug

Saving a new completion while keeping the default name persists it and then removes it from the in-memory list, diverging UI from storage. newCompletion() creates an item named "New Completion"; UpsertCompletionView.save() writes the fields and calls onSave() (CompletionsStore.save persists the whole array), then dismisses. The sheet's .onDisappear checks `selectedCompletion.name == "New Completion"` and calls discard(for:), which filters the item out of the `completions` binding but never calls onSave/onDelete. Repro: click New Completion, type an instruction, leave the name as "New Completion", click Save -> the completion is written to SwiftData but vanishes from the editor list and from the panel (PromptPanel reads completionsStore.completions); it reappears after relaunch when load() refetches. Any subsequent save persists the array without it, silently deleting the just-saved item.

### `Molten/UI/macOS/Components/CompletionPanelView.swift:161-178` — bug

Bare-letter completion keyboard shortcuts intercept typing in the custom-command TextField. Each completion button installs `.keyboardShortcut(KeyEquivalent(completion.keyboardCharacter), modifiers: [])` (line 169) and these buttons remain in the hierarchy while the custom instruction TextField is shown (lines 176-178; showIf only removes the TAB button, not the completion buttons). Modifier-less keyboard shortcuts are matched as key equivalents before keyDown delivery to the focused text field, so typing a letter that matches a completion fires that completion instead of inserting the character. Repro: open the panel with text selected, press TAB to open Your Command, type "fix this" -> pressing "f" immediately submits the Fix Grammar completion (submitCompletion) and collapses the list, making the custom instruction field unusable for most text.

### `Molten/UI/macOS/Components/PromptPanelView.swift:24-33` — bug

The panel's Cmd+V handler replaces the entire prompt and unconditionally attaches any clipboard image. On Cmd+V it sets `prompt = clipboardText` (overwriting, not inserting at the cursor) and also attaches an image whenever the clipboard contains one. Repro 1: type a question in the panel, copy text elsewhere, press Cmd+V -> the typed question is discarded and replaced by the clipboard text. Repro 2: copy rich content from a browser (clipboard holds both text and an image), press Cmd+V to paste text -> an image is silently attached and will be sent to the model along with the prompt. Paste should insert at the cursor and only attach an image when the clipboard is image-only (or on explicit user action).

### `Molten/UI/macOS/PromptPanel/PanelCompletionsVM.swift:43-88` — bug

sendPrompt has no busy-state protection and overwrites generationTask without cancelling the previous one. `isReady` is declared false and never set true anywhere in the codebase, so the `!isReady` guard never blocks; a second sendPrompt while a stream is active assigns a new generationTask (line 54), orphaning the first stream's Task (it keeps running and enqueuing into sentenceQueue). The outer reachability Task (line 52) is also untracked. Repro: trigger an in-window completion, reopen the panel and trigger another before the first finishes -> two streams interleave their chunks in the shared paste queue, producing garbled output in the target app, and cancel() only stops the latest stream.

### `Molten/UI/macOS/PromptPanel/PanelCompletionsVM.swift:91-123` — bug

handleReceive spawns an unstructured Task per stream chunk that is not tied to generationTask cancellation, so cancelled completions keep feeding the paste queue. PanelManager.handleNewMessages cancels generationTask and drains sentenceQueue when the user switches apps (PanelManager.swift:44-48), but already-spawned handleReceive Tasks still run `await sentenceQueue.enqueue(...)` afterwards; on the next 0.1s tick lastPrintApplication is nil so the focus guard is skipped and the leftover chunks are pasted into whatever app is now active. Repro: trigger an in-window completion in app A, immediately switch to app B while it is streaming -> a fragment of the LLM response is typed/pasted into app B's document. Additionally, because each chunk enqueues from a separate Task, actor hop order is not guaranteed to match stream order, so pasted text can be scrambled; and `messageResponse = messageResponse + responseContent` is an O(n^2) main-actor concatenation of a value that is never read anywhere (grep: only written at lines 50 and 120).

### `Molten/UI/macOS/PromptPanel/PanelManager.swift:13-19` — performance

Printer.write blocks a Swift cooperative-pool thread with usleep. The Printer actor calls usleep(50000) and then Accessibility.simulatePasteCommand(), which itself usleeps another 50000 between the Cmd+V down/up events (Helpers/Accessibility.swift:163) -> ~100ms of synchronous blocking per write. handleNewMessages drives this from an AsyncTimerSequence ticking every 0.1s, so during an in-window completion a cooperative thread is blocked nearly continuously, violating the cooperative pool's forward-progress contract and starving other tasks sharing the pool. Use Task.sleep / async delays instead of usleep inside the actor.

## Adjudications & context

- **Watcher prune (Watchers.swift:233-247):** unconditional base+name row removal was the *deliberate* K-D5 fix (commit `d83b2f4`, "document removal always drops the index row") to cure stale counts. The reported defect is a residual edge of that fix: two live files sharing one base+name (e.g. same filename in different subfolders) collide in the single-name schema, and deleting one drops the survivor's row with no re-ingest path. Reported as high because the loss is silent and permanent, but it is a narrow-input regression trade-off, not a careless bug.
- **⌘V interception (InputFields_macOS.swift:52-61):** one batch flagged this high, another dismissed it as "Edit-menu routing likely handles text paste". Adjudicated in favor of the finding after reading the mechanism: `DisableSoundsNSView.performKeyEquivalent` ignores the passed event, polls physical key state, and returns `true` on any Cmd+V match — consuming the key equivalent at the view-hierarchy stage even when the clipboard holds no image (the action only handles images). `PromptPanelView.swift:24-31` explicitly compensates with clipboard-text handling, evidence the interception does swallow text paste. The main chat input has no such compensation.
- **OllamaKit / Magnet / mlx internals:** SPM checkouts live outside the approved working folder; findings depending on their unverifiable internals were discarded rather than speculated.
- **Known-intentional patterns not reported as defects:** `.shared` singletons with `nonisolated(unsafe)`, array-buffer + Throttler streaming, `cloudKitDatabase: .none`, empty-URL-disables-provider semantics, backoff ladder timings, BGTask registration in `MoltenApp.init()`, position-based embedding attention mask, KnowledgeCleanup's conservative completeness gate. Concrete races/bugs *within* these patterns were still reported.
